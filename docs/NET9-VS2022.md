# .NET 9 / Visual Studio 2022 compatibility

Branch: `net9`. Evaluated on 19 September 2026. `main` retains the original .NET 10 configuration.

## Open this branch in Visual Studio

1. Close any running debugging session before switching branches.
2. Run `git switch net9` in the API repository.
3. Use Visual Studio 2022 **17.14** with the ASP.NET and web development workload and .NET 9 SDK installed. This machine has VS 17.14.37111.16 and SDK 9.0.312.
4. Open `Sparta.sln`. All nine repository projects target `net9.0`.
5. Restore NuGet packages and build the solution. DevExpress packages require the configured licensed package source/local installation.
6. Set **Sparta.Api** as the startup project and select its **http** profile. Start debugging, then open `http://localhost:5180/swagger`.
7. For Aspire orchestration, set **Sparta.AppHost** as the startup project instead. Use its HTTP profile and the dashboard/resource URLs printed at startup. Stop a standalone API first if it occupies the same port.

The repository pins SDK 9.0.312 with `latestPatch` roll-forward and prerelease disabled. Installing SDK 10 alongside SDK 9 is fine: commands under this repository select SDK 9. A later 9.0.3xx patch can satisfy the pin; a machine with only an older patch must install a suitable SDK.

[Microsoft's compatibility matrix](https://learn.microsoft.com/en-us/dotnet/core/porting/versioning-sdk-msbuild-vs) pairs VS 17.14 with SDK 9.0.3xx. Merely changing TargetFramework while keeping the original 10.0.301 SDK pin would not provide the intended VS 2022 toolchain.

## Package decisions

| Component | Original | net9 branch | Reason |
|---|---|---|---|
| Shared target framework | net10.0 | net9.0 | Applies to business libraries, API and tests |
| Explicit ServiceDefaults/AppHost targets | net10.0 | net9.0 | Overrides also need retargeting |
| SDK pin | 10.0.301 | 9.0.312 | Installed SDK compatible with VS 2022 17.14 |
| DevExpress XAF packages | 26.1.4 | Unchanged | Their compatible assets restore and build on net9 |
| EF Core / dotnet-ef | 8.0.28 | Unchanged | Preserve existing XAF EF generation and migrations |
| Microsoft.AspNetCore.Authentication.JwtBearer | 10.0.9 | 9.0.20 | ASP.NET Core package must support the target framework |
| Microsoft.AspNetCore.Mvc.Testing | 10.0.9 | 9.0.20 | Test host aligned with ASP.NET Core 9 |
| Microsoft.Identity.Web | 4.14.2 | Unchanged | Compatible; Entra integration assertions pass |
| Swashbuckle / Annotations | 6.9.0 | Unchanged | Compatible with current Swagger wiring |
| Microsoft.Extensions.Http.Resilience | 10.8.0 | Unchanged | Package includes net9 assets; package major is not the target framework |
| Microsoft.Extensions.ServiceDiscovery | 10.8.0 | Unchanged | Package includes net9 assets |
| OpenTelemetry packages | Existing 1.15.x versions | Unchanged | Restore and compile for net9 |
| System.Security.Cryptography.Xml | 10.0.11 | Unchanged | Includes net9 assets; retain existing patched dependency |
| Aspire AppHost SDK | 13.5.4 | 9.5.2 | Aspire 13 requires SDK 10 |
| Aspire.Hosting.AppHost | Implicit in newer SDK model | Explicit 9.5.2 | Use Aspire 9's project structure |
| MessagePack (AppHost dependency) | 2.5.192 via Aspire 9 / StreamJsonRpc | Explicit 2.5.303 | Override vulnerable transitive version within the same major line |

Aspire.AppHost uses the `Microsoft.NET.Sdk` project SDK plus `Aspire.AppHost.Sdk/9.5.2`, explicit hosting package and `IsAspireHost=true`. The Aspire 13 CLI-bundle property was removed. See [Aspire 13 requirements](https://aspire.dev/whats-new/aspire-13/) for why keeping the original host prevents an SDK-9-only build.

Aspire 9 also requires `ASPIRE_ALLOW_UNSECURED_TRANSPORT=true` for the existing local HTTP launch profile. This is set only on that profile; the HTTPS profile is preserved. Without this setting the host rejects startup with an OptionsValidationException.

The vulnerability scan initially found MessagePack advisories in the Aspire 9 dependency graph. The explicit patched dependency addresses the discovered old version; it is not a suppression. See the [MessagePack maintainer advisory](https://github.com/MessagePack-CSharp/MessagePack-CSharp/security/advisories/GHSA-hv8m-jj95-wg3x). Re-run the scan periodically because advisory data changes.

## Web UI boundary

The sibling `Build Sparta Web` repository still targets .NET 10. The net9 AppHost excludes both its project reference and its resource registration. Otherwise, restoring this API solution with SDK 9 could pull in an incompatible project outside this repository.

This change does not retarget or edit the Web UI repository. The UI can be run separately with its own SDK and configured API base URL. Migrating that UI to .NET 9 requires its own branch and package review, especially the ASP.NET Core OpenIdConnect package and Blazor behavior.

## Databases and configuration

No schema change or migration is required solely for this retarget. The four database contexts, EF migration files, connection-string keys, User Secrets ID, local JWT configuration and Entra identity mapping remain the same.

Existing User Secrets are reused. Do not rerun initialization or reset seed passwords simply to switch framework branches. Only apply migrations when an actual schema change requires them.

Use the .NET 9 Hosting Bundle on an IIS deployment of this branch. Update SDK/runtime servicing patches through the normal machine maintenance process; this change does not install or update Visual Studio or system runtimes.

## Verification commands

From the repository root:

```powershell
dotnet --version
dotnet tool restore
dotnet restore Sparta.sln
dotnet build Sparta.sln -c Release --no-restore
dotnet ef dbcontext list --project src/Sparta.Api --startup-project src/Sparta.Api --configuration Release --no-build
dotnet run --project tests/Sparta.IntegrationTests -c Release --no-build
dotnet list Sparta.sln package --vulnerable --include-transitive
```

The integration harness uses configured development SQL databases and creates test records. It is not a read-only check. It runs as an executable, not `dotnet test`.

To explicitly test the installed VS 2022 build engine:

```powershell
& 'C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe' `
    Sparta.sln /t:Build /p:Configuration=Release /m:2 /v:minimal /nologo
```

Adjust the edition directory if using Professional or Enterprise.

Actual Entra browser consent/redirect configuration and Visual Studio F5 interactions require their own interactive checks; a successful MSBuild run is not an interactive IDE test.
